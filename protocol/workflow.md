# 数学建模 Agent 工作流

## 0. 任务接收与目标批准

输入：题面、附件、用户目标、比赛截止时间、允许/禁止的方法和交付格式。

产物：

- `case_manifest.yaml`
- `artifacts/problem_contract.md`
- `artifacts/decision_log.md`
- `artifacts/claim_register.md`

退出条件：用户确认研究目标、题目范围、数据边界和语言/论文格式。没有目标批准，不启动长时间多代理工作流。

## 1. 原始资料冻结

1. 收集题面、附件、字段说明、论文和代码。
2. 记录来源、获取时间、文件大小和 SHA-256。
3. 原始资料放入 `input/` 或 `source/`，只读保存。
4. 建立字段字典、单位表、标签定义、训练/测试边界和禁止使用字段。

退出条件：所有进入模型的输入都有明确来源和解释；无法解释的字段标记为 `unknown`，不得默认猜测。

## 2. 双路独立建模

### Codex 主路

Codex 先独立完成：题目拆解、可行 baseline、数据读取和最小实验，并将模型假设写入 `artifacts/`。

### Claude 盲审路

Claude 只看原始题面、数据契约和验收标准，独立提出模型结构、反例、数据风险和应有测试；不读取 Codex 的完整答案。

产物：`reviews/<id>_claude_blind.md`。

## 3. Baseline 阶段

先完成最简单、可解释、可复现的模型：

- 2023 E：患者级数据切分 + 一个统计/树模型 + 基本校准/误差指标；
- 2019 F：小图穷举 + BFS/Dijkstra；
- 2025 A：DAG 拓扑检查 + list scheduling + 缓存峰值模拟。

退出条件：baseline 能运行，输入输出可解释，至少有一个小规模或人工可验证案例。

## 4. 候选模型与实验

Codex 可以提出复杂模型，但每个候选必须有实验卡：问题、假设、数据版本、代码版本、参数、随机种子、指标、图表和限制。

不要同时开启过多候选。优先选择能回答题目、能验证、能解释的模型，再考虑提升分数。

## 5. 确定性验证

验证顺序建议为：

1. 文件/数据契约；
2. 小样本手算或穷举；
3. 公式和维度；
4. 约束和边界；
5. 指标和统计稳定性；
6. 代码测试和独立复跑；
7. 大规模运行。

任何确定性验证失败，都要进入 `failures/`，并把相关 claim 降级为 `disputed` 或 `rejected`。

## 6. 对抗审查

把 Codex 的模型摘要、代码版本、运行摘要和 claim register 交给 Claude。Claude 不改主方案，只写审查结果：

- 哪些结论有直接证据；
- 哪些假设过强；
- 能否构造反例；
- 哪些约束/数据泄漏/指标问题会推翻结论；
- 最小修复和应补实验。

P0/P1 问题阻断后续定稿。

## 7. 修复和独立复现

Codex 根据审查结果修复后，必须生成新运行 ID。旧运行、旧结果和旧审查不能覆盖。复现者按照记录执行，不读取作者的隐藏推理，不手动补参数。

## 8. 论文与答辩材料

最终论文只引用 `supported` 或 `supported_with_limits` 的 claim。每个强结论都要能回溯到：

```text
题面/数据源 → 数据契约 → 模型/代码 → 运行记录 → 审查报告 → 最终结论
```

未解决争议、失败算法、敏感性边界和无法复现的结果必须在交接记录中保留。
