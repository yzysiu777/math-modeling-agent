# 华为杯竞赛核心工作流

本工作流只有一条主线，适用于运筹优化、数据分析和混合建模。它服务于四天赛程：
前期扩大方法空间，中期用实验收敛，后期把稳定结果同步写成论文。

工作由三个独立会话接力完成：建模手（`prompts/modeler.md`）、编程手
（`prompts/engineer.md`）、写作手（`prompts/writer.md`），靠落盘契约交接，见
`prompts/contracts/`。

路由由建模手读题面判断，`scripts/router.py` 只作交叉参考。案例创建后，队员在
`checkpoint.yaml` 中确认或修正一次正式路由；提醒和阻断由同一个
`scripts/check_case.py` 按当前阶段给出，不新增另一套竞赛模式。

```text
题意重构                                    建模手
  -> 头脑砖暴：发散 ≥6 条，收敛 ≥3 条        建模手
  -> 七维度评估，决定先跑哪条 probe          建模手
  -> probe 轻测试证伪                        建模手出规格，编程手跑
  -> 通过的路线写 full 规格                  建模手
  -> 忠实实现 + 独立复算 + 出图              编程手
  -> Champion / Challenger                   建模手提议，队员定
  -> Independent Reviewer C1/C2/C3           队员手动触发
  -> 深化模型与稳健性实验                    建模手 + 编程手
  -> 论文同步写作 + 数字溯源                 写作手
  -> 最终数值与格式检查                      写作手 + 队员
```

## 1. 题意重构

从题面直接提取子问题、输入、输出、目标、硬约束、字段、单位、时间边界、评价
指标和交付物。只把会改变路线的歧义交给队员确认；其他未知先写入“尚缺信息”，
允许可逆探索。路由只有 `optimization`、`data_analysis`、`hybrid` 和
`insufficient_information`。

## 2. 头脑砖暴与候选模型池

先**发散**：每个关键子问题无过滤地列 ≥6 条想法，跨方法族取样，刻意包含一条极简路线
和一条超预算路线来框定上下界。再**收敛**：筛到至少三条方法论不同的路线。

「真正不同」的判据是：路线 A 因为某个假设失败时，路线 B 会不会因为同一假设失败？

路线卡必须有核心思想、数学表达、关键假设、数据需求、实现/运行成本、预期优势、风险
和最便宜的证伪实验。评估用七个固定维度（预期效果、实现成本、运行成本、数据满足度、
可解释性、论文价值、风险）写进 `models/comparison.md`，结论必须落到「先跑哪条 probe」。

可先读取 `.agents/skills/competition-modeling/references/` 下对应的实战方法卡、
`brainstorming.md` 和 `route-evaluation.md`。
`scripts/model_pool.py` 只检查空字段、非法状态、重复路线 ID 和明显重复的方法族；真正
的方法论差异仍由 Codex、Independent Reviewer C2 与队员判断。例如 MIP 的 arc-flow、path-flow、
time-indexed 表述是否足够独立，不能由这个语法检查器自动决定。

运筹题按适用性覆盖精确规划、网络/动态规划、分解或松弛、启发式/元启发式、鲁棒
或随机优化、仿真优化。数据题按适用性覆盖描述统计、线性/广义线性、树模型、时序、
聚类和神经网络。混合题写清分析输出到决策模型的字段、单位、误差和场景规则。

## 3. 轻测试先行与实现规格

每条留下来的路线**先写 probe 规格**（`templates/spec_probe.md`）：找出它最可能不成立
的那条假设，用 ≤50 行代码、≤1 分钟去打它，判据在写代码之前定死。probe `FAIL` 是好
结果 —— 一分钟换掉一条错路。

probe 通过后才写 full 规格（`templates/spec.md`），八段齐全：目标与判据、数学表述、
数据契约、算法、输出契约、复算要求、明确不做、未决问题。写完自检：看不到本会话的
编程手，只读这份文件能不能唯一确定实现？

编程手按规格实现，**不得修改模型**。规格没覆盖的建模决策写 `.questions.md` 并停止该
条路线；纯工程决策自己定。Python 和 MATLAB 并列主力，由规格的 `language` 字段决定，
但关键结论的复算必须有 Python 版本 —— 阶段检查和 CI 只能运行 Python。

```bash
make spec-check CASE=cases/<case_id>
```

## 4. Baseline 与实验赛马

先跑小规模、手算、穷举、合成数据或短迭代。优化题先有规则、线性模型、网络算法
或小规模规划；数据题先有统计量、朴素预测或线性模型；混合题先连接简单分析器
和决策器。实验使用统一切分、约束口径、实例范围和指标，优先选择能区分路线且
成本低的实验。

实验板的每一行至少说明实验 ID、候选路线、问题、最小配置、数据/实例范围、指标、
成本、状态、结果摘要、是否继续投入和下一项信息价值最高的实验。保留 Champion
与至少一个方法论不同的 Challenger；淘汰路线只保留简短理由和证据。

结果统一落盘到 `experiments/outputs/`：`data/` 放结果 CSV/JSON，`figures/` 放
PDF + PNG 并回填 `manifest.md`，`checks/` 放复算报告。复算报告的失败项会被
`scripts/check_case.py` 自动读取并点亮确定性风险标志，因此必须照实写。

普通数据、实验输出和中间文件记录来源、日期、大小和可复现命令。官方文件、最终提交
PDF 或团队指定的里程碑版本可以额外记录 SHA-256，方便确认文件身份。

## 5. 三个关键挑战

- C1：题意、目标、约束、单位和遗漏；必要时盲审；
- C2：模型架构、算法、公式—代码一致性、替代方法族和反例；
- C3：主要结果、对照公平性、泄漏、稳定性、数字来源和论文强结论。

用 `make review-packet CASE=... NODE=C2` 生成审核包草稿，主 Agent 补完最担心的问题和
3–5 个待答问题，队员复制到全新会话。每次给 Independent Reviewer 的包只保留完成该节点
所需内容。Independent Reviewer 不
重跑整题，只输出最高风险问题、方法论不同的挑战视角、最便宜的区分实验、路线建议、
人工决定和未检查范围。包和报告注明 `reviewer_provider`、`reviewer_model`、
`review_session: fresh`、`saw_main_conversation: false` 和 `critical_node`；provider
值允许扩展，不构成厂商白名单。
队员把采纳/拒绝及原因写入 `decisions.md`。

## 6. 阶段检查与主动提醒

同一条主线按时点运行轻量检查：

| 时点 | 命令 | 预期行为 |
|---|---|---|
| 题意和便宜实验 | `make case-check CASE=... STAGE=exploration` | 路由未确认、单次失败等只提醒，不阻止探索 |
| 冻结 Champion/正式模型 | `make case-check CASE=... STAGE=model_selection` | 未确认路由阻断；缺 C2、缺规格、跳过 probe、重复失败或效果担忧提醒 |
| 写摘要、结论或强主张 | `make case-check CASE=... STAGE=paper_claims` | 缺 C3、确定性严重错误阻断；claim_map 不可追溯提醒 |
| 最终提交 | `make final-check CASE=...` | 另查规格、人工决定、claim_map 可追溯和 LaTeX/PDF QA |

每条输出都包含稳定编号、触发原因、责任人、建议节点和是否阻断。失败摘要的内容由
实验成员记录，检查器不使用关键词表猜测失败原因；不可行、目标复算不一致、切分重叠
和泄漏等阻断只来自已实际运行的确定性检查 —— 优先由 `experiments/outputs/checks/*.json`
的复算报告自动点亮，`checkpoint.yaml` 中人手填写的标志作为覆盖手段。普通失败和可逆探索继续
进行，不把提醒变成重型审批流程。

## 7. 深化与论文

路线确定后再扩大规模、做敏感性/稳健性/消融和误差分析。实验一稳定，就同步维护
符号表、公式、算法、图表需求、结果段和引用。不要等所有代码完成才写论文。

## 8. 最低质量检查

- 题面和原始附件没有被覆盖，字段和单位明确；
- 数据切分、标签生成和泄漏风险已经检查；
- 优化解的约束与目标已经独立复算；
- 关键统计指标、随机种子、参数、代码入口和输出可复现；
- 论文公式、代码、图表、引用和结论一致；
- LaTeX 编译、引用、匿名信息、PDF 文本和版式通过检查；
- 当届官方模板、AI 规定和提交手册已在比赛日重新核对。

## 9. 四天节奏建议

| 时段 | 主要角色 | 重点产出 |
|---|---|---|
| 第 1 天 | 建模手 → 编程手 | 题意重构、发散收敛出三条以上路线、probe 规格与 probe 结果、baseline |
| 第 2 天 | 建模手 ↔ 编程手 | full 规格、实验赛马、Champion/Challenger、C2、复算报告 |
| 第 3 天 | 编程手 → 写作手 | 稳健性/敏感性、图表定稿、C3、结果与讨论段落、claim_map |
| 第 4 天 | 写作手 + 队员 | 摘要结论统一核数、数字溯源复核、格式/匿名/引用检查、PDF 和人工提交确认 |

第 1 天不要急着写 full 规格。当天最高价值的产出是「用便宜实验淘汰掉两条错路」，
而不是「把一条路写到一半」。
