# 契约一：SPEC（建模手 → 编程手）

一条候选路线一份规格，落在 `cases/<case_id>/specs/`。字段模板见
`templates/spec.md`（full）和 `templates/spec_probe.md`（probe）。

## 两种规格

| | probe | full |
|---|---|---|
| 目的 | 判断路线值不值得深入 | 产出论文级结果 |
| 预算 | ≤50 行代码、≤1 分钟、玩具规模 | 按题目实际需要 |
| 判据 | 单一数值判据 | 完整通过/失败判据 |
| 复算 | 可以只对真值比对 | 必须逐条约束 + 目标值独立重算 |
| 出图 | 不要求 | 按输出契约必出 |

**顺序规则：一条路线必须先有 probe 且已跑完回填 `experiments/board.md`，才允许写 full
规格。** 例外只有一种：题目要求的方法唯一且无可替代（例如题面直接指定算法），此时在
full 规格第 7 段写明跳过 probe 的理由。

## 建模手的义务

1. 每段都要能被**看不到本会话的人**唯一解读。写完后逐段自检一遍。
2. 判据必须可判定 —— 数值、布尔或明确的比较关系。「效果好」「收敛正常」不是判据。
3. 符号与 `models/candidates.md`、论文符号表保持一致；同一个量不在两处用不同符号。
4. 自己知道没定的事，全部写进第 8 段「未决问题」。**第 8 段为空是一个可疑信号** ——
   真实建模过程很少一次定完所有细节。
5. 规格改动后更新 `spec_id` 对应文件并在 `decisions.md` 记一条（仅当改动影响目标、
   硬约束或结论强度时）。

## 编程手的权利

收到规格后，编程手**有权拒绝开工**并回问，当出现：

- 判据不可判定；
- 约束条件之间矛盾，或与目标函数单位不一致；
- 数据契约里的字段在实际输入文件中不存在；
- 输出契约没写清列名或路径；
- 复算要求为空（full 规格）。

拒绝开工不是消极 —— 照着有歧义的规格实现，代价比回问大得多。

## 编程手的义务

1. **只按规格实现。** 规格写了什么就实现什么，不多不少。
2. 觉得规格里的方法不好，**照做，然后在实验记录里写下你的观察**。改进意见通过回问
   或实验证据反馈，不通过擅自改实现表达。
3. 实现与规格不一致的地方（包括为了跑通做的任何妥协），必须在 `board.md` 的结果摘要
   里写明。

## 检查

```bash
make spec-check CASE=cases/<case_id>
```

`scripts/check_spec.py` 只检查字段齐全、状态合法、判据非占位、full 规格的输出契约
与复算要求非空。**它判断不了建模是否正确，也判断不了判据是否合理** —— 那由 C2 独立
审核和队员判断。
