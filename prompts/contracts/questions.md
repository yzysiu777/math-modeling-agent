# 契约三：回问（下游 → 上游）

下游撞到上游没定的事时，写 `cases/<case_id>/specs/<spec_id>.questions.md`，模板见
`templates/spec_questions.md`。

## 唯一的判断标准

**这个决定会不会改变目标、约束、指标定义、数据口径或结论强度？**

会 → 建模决策 → 回问，停止该条路线。
不会 → 工程决策 → 自己定，继续做。

## 对照表

| 情形 | 类别 | 动作 |
|---|---|---|
| 约束在某实例下不可行，要不要松弛 | 建模 | 回问 |
| 参数没给取值范围 | 建模 | 回问 |
| 指标是按样本平均还是按类别平均 | 建模 | 回问 |
| 缺失值规格没写怎么处理 | 建模 | 回问 |
| 切分比例没写 | 建模 | 回问 |
| 求解超时了要不要放宽 gap | 建模 | 回问 |
| 用 `dict` 还是 `DataFrame` 存中间结果 | 工程 | 自己定 |
| 用 PuLP 还是 OR-Tools | 工程 | 自己定 |
| 循环还是向量化 | 工程 | 自己定 |
| 日志打到文件还是标准输出 | 工程 | 自己定 |
| 文件怎么命名、代码怎么分模块 | 工程 | 自己定 |
| 图的具体配色（规范内） | 工程 | 自己定 |

边界情况：**分不清就当成建模决策回问。** 多问一次的成本，远低于整条路线基于错误
假设跑完再推倒。

## 下游的义务

1. 回问时带上**倾向的选项和理由**，不要只抛问题。上游做选择比做填空快得多。
2. 写清阻塞范围：`blocked`（整条路线停住）还是 `partial`（其余部分继续）。
   `partial` 时继续做不受阻的工作，不要空等。
3. 列出已经确认过的事实，避免上游重复排查。

## 上游的义务

1. 答复写进 `.questions.md` 的「上游答复」表，**同时更新对应规格文件** ——
   只在回问文件里答复，规格会和实现脱节。
2. 答复如果改变了目标、硬约束或结论强度边界，在 `decisions.md` 记一条。
3. 如果同一份规格反复被回问同类问题，说明规格写得不够具体，重写该段而不是逐条答复。

## 反模式

- 回问工程问题 —— 说明下游在推卸本该自己做的判断；
- 从不回问 —— 通常说明下游在替上游做建模决定，比回问太多危险得多；
- 上游答复「你看着办」—— 这不是答复，是把建模决策丢给了下游。
